# Rule Set: Requirements Documents

Scope examples: `requirements/**`, `docs/spec/**`, similar requirement artifacts.

## Structure requirements
Use these headings where practical:
1. Background
2. Requirement(s)
3. Rationale
4. Acceptance criteria
5. Open questions

## Rules
- Keep requirements implementation-agnostic where possible.
- Avoid embedding low-level design details unless explicitly needed.
- Prefer stable IDs for requirements (e.g., `REQ-001`).
- Make acceptance criteria testable and observable.
